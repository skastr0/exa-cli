# Publishing

This repository is prepared for a first experimental npm release, but this file does not authorize public repository visibility changes, tag pushes, workflow dispatches, GitHub releases, or registry uploads.

## Public Promise

`exa-cli` is experimental. Version `0.y.z` means the command contract is usable for local agent and script workflows, but command behavior, JSON envelopes, schemas, and package boundaries may change. User-visible breaking changes should be documented in `CHANGELOG.md`.

## Channels

The first public channel is npm only.

The CLI is Bun-native. Do not publish the raw Bun entrypoint as an npm executable and promise broad runner compatibility. npm runner support uses the same wrapper pattern as `../pulsar` and `../background-tasks`: a main package, per-platform optional packages, and a small Node launcher.

GitHub Releases and Homebrew are deferred until the npm binary package shape is stable. JSR is deferred.

## Publishable Packages

Publish these npm packages in dependency order:

1. `@skastr0/exa-cli-darwin-arm64`
2. `@skastr0/exa-cli-darwin-x64`
3. `@skastr0/exa-cli-linux-arm64`
4. `@skastr0/exa-cli-linux-x64`
5. `@skastr0/exa-cli`

The root workspace package `@skastr0/exa-cli-workspace` remains private and is not a publish target.

## npm CLI Package Layout

The npm runner packages live under `packages/npm/*`.

- `packages/npm/exa-cli` defines the public `@skastr0/exa-cli` package and exposes `bin["exa-cli"]`.
- `packages/npm/exa-cli/bin/exa-cli.js` is a tiny Node launcher. It detects `process.platform` and `process.arch`, resolves the matching platform package, and spawns its Bun-compiled binary.
- `packages/npm/exa-cli-darwin-arm64`, `packages/npm/exa-cli-darwin-x64`, `packages/npm/exa-cli-linux-arm64`, and `packages/npm/exa-cli-linux-x64` define the platform packages. Their `bin/` directories are generated by `bun run build:npm-cli` and intentionally ignored by git.
- The platform packages must be published before `@skastr0/exa-cli` because the launcher declares them as exact-version `optionalDependencies`.

## Local Verification

Before first publish:

```bash
bun install --frozen-lockfile
bun audit
bun run verify
bun run smoke:npm-cli
bun run pack:dry-run
bun run publish:dry-run
```

Inspect the `npm pack --dry-run` output for each package and confirm:

- the public launcher package contains `bin/exa-cli.js`, `README.md`, and `LICENSE`
- each platform package contains `bin/exa-cli` and `LICENSE`
- package metadata, repository links, license fields, `os`, and `cpu` fields are correct
- package tarballs do not include logs, state, credentials, local payloads, provider responses, or generated private artifacts
- no publishable package depends on `workspace:*`

## GitHub Setup

For the public repository posture:

- enable secret scanning and push protection
- enable Dependabot alerts and dependency graph
- enable private vulnerability reporting
- keep issues enabled
- keep Discussions, Wiki, and Projects disabled unless there is a clear support plan
- protect the default branch once external PRs are accepted

Before npm publishing:

- create or confirm access to the `@skastr0` npm scope
- configure npm trusted publishing for `.github/workflows/npm-publish.yml`
- use the protected `release` GitHub environment for publish jobs
- configure the trusted publisher for every package, including `@skastr0/exa-cli` and the platform packages
- if npm cannot configure trusted publishing before the first publish, create a temporary granular npm token with package/scope read-write access and npm's 2FA-bypass option enabled, store it as a `release` environment secret named `NPM_CONFIG_TOKEN`, publish once through CI, configure trusted publishing for the now-existing packages, then revoke the token

## First Release Sequence

1. Confirm the repository is public and the public docs/security settings are ready.
2. Run local verification and package dry-runs.
3. Confirm public docs, security policy, issue templates, and package metadata.
4. Configure GitHub security settings and npm trusted publishing.
5. Push `v0.1.0` only after the maintainer gate.
6. Let CI publish packages.
7. Verify package pages, package provenance, metadata, and install commands from a clean temporary directory.

## Rollback Notes

npm package versions should be treated as permanent. Prefer publishing a fixed patch version over relying on unpublish. If a bad first release happens, deprecate the affected version with a clear replacement message and publish a corrected patch version.
